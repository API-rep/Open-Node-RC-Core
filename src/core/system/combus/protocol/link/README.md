# The Link Manager

Which port carries which channels, in which direction, at what rate? The code never says: the configuration does. The link manager turns these few lines into links that run, then keeps an eye on them.

## Describing a Link

A link has two ends: two boards of a node, or two nodes. Both must agree on what travels, and neither needs to know how the other is wired. So a link is described once, as a **`ComDev`**, and both ends share that same description.

A `ComDev` says what the link is:

- its scope: [between nodes or inside a node](../../../../../../doc/linking_nodes.md#two-kinds-of-links), which sets the channels it carries;
- its type: one way or both ways;
- its activation: always, or only once [coupled](../coupling/README.md);
- its protocol, a `ComProtocolCfg`: line rate, frame rate, loss timeout and startup grace;
- its table, a `ComPeerLink` generated by the builder: the set of channels both nodes exchange, seen from this end (on a link between nodes only);
- its role: a [command source](../../../input/~README.md), such as the link from a remote, hands its frames to its module, which writes them to the ComBus when it drives.

Every link, between boards or between nodes, is described by this same `ComDev` configuration structure, so no link needs code of its own. And a `ComDev` never says over what it runs: that is the business of the port.

In parallel, a port is built on the same principle: one standard `ComPort` for every kind of [hardware port](../../../hw/README.md), used through the same read and write calls. A `ComDev` and a port are thus made to be plugged into each other.

Finally, the **`ComDevMap`** plugs a `ComDev` on a port. Moving a link is then only a matter of plugging it elsewhere: the same `ComDev` can run over a wire today, and over a radio tomorrow, by changing a single line.

## Why a Link Manager

In the configuration, a link is only a description: something must safely bring it to life, and keep it working. That is the job of the link manager, in two parts:

- **At boot, the setup.** A description can be wrong, and two links can claim the same port: nothing may travel before each link is checked and started. Without the setup, each board would have to wire its links in its own code.
- **While it runs, the supervisor.** A wire comes loose, a remote goes out of range: a silent link sends no error. Without the supervisor, a lost link would go unnoticed.

```text
┌────────────────────────────────────────────────────────┐
│  MACHINE                                               │
│    boot: com_init() ──► board_links_init()             │
│    loop: com_rx_update(), com_tx_update()              │
└────────────┬───────────────────┬───────────────────────┘
             ▼                   ▲
┌─ LINK MANAGER ──────────────── │ ──────────────────────┐
│  at boot: link init            │                       │
│   └► ComDevMap ──► ComBusLink  │                       │
│  at run:  link supervisor      │                       │
│   └► follows each ComBusLink   │                       │
│                                ▼                       │
│  ┌─────────────────────────────┴────────────────────┐  │
│  │  PROTOCOL                                        │  │
│  │    TX, RX, frame, handshake,                     │  │
│  │    on each ComBusLink                            │  │
│  └─────────────────────────────┬────────────────────┘  │
│                                ▲  write()              │
│                                │  readByte()           │

│  │  HARDWARE                                        │  │
│  │    ComPort: set up from the ComPortCfg           │  │
│  │    port: UART, ...                               │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

## At Boot: the Setup

The machine calls the setup once, from `board_links_init()`, with the table of `ComDevMap` of its board. Each link goes through four steps:

1. **Check.** The `ComDev` and its plugging are refused if they cannot work: a missing piece, a direction that does not match the wiring, a frame rate or a loss timeout that makes no sense, a line too slow or too loaded for what it must carry. A line close to its limit, or a loss timeout only just longer than the frame period, only gives a warning.
2. **Set up the port.** The adapter of the kind of port sets it up, and gives its `ComPort`. Only the pins of the directions this end uses are taken.
3. **Build.** The `ComDev` and the `ComPort` just set up become a **`ComBusLink`**, the running link the protocol works with.
4. **Start.** The contract is prepared, the TX and RX sides start, and the link is handed to the supervisor. A link through a [coupler](../coupling/README.md) starts off, until it is paired.

A refused link stays inactive and is reported in the log; the others start anyway. Nothing is allocated: the storage of the links is static, and belongs to the board.

A started link does not carry data yet: both ends first agree on their channels, through the [handshake](../handshake/README.md). Until then, the data frames received are ignored.

## At Runtime: the Supervisor

On every loop cycle, right after the reception, the supervisor brings each receiving link up to date:

| State | Meaning |
|---|---|
| `NEVER_SEEN` | no frame since the link started |
| `ALIVE` | a recent data frame, under a valid contract |
| `LOST` | seen, then silent for longer than its loss timeout |

When a link counts as lost depends on what it connects:

- **Between boards**: `LOST`, or never seen once the startup grace is over, since the boards start together. It feeds `BOARD_LINK_FAIL`.
- **To another node**: as soon as it is not `ALIVE`, without any grace, since the other node may simply not be there. It feeds `NODE_LINK_FAIL`.
- **Through a coupler**: it feeds the contributor of its coupler, see [coupling](../coupling/README.md).
- **From a command source**: the [source manager](../../../input/~README.md) follows it, not the supervisor: a machine driven by another source is not at fault because its remote is away.

A send-only link never counts: it knows nothing of the other end.

When a link with a table stops being alive, the channels it brought return to their safe value, the one declared in the `.cb`; what the node sends does not move. In the same cycle, the [failsafe](../../../failsafe/failsafe_module.md) reads the contributors and decides the severity.
