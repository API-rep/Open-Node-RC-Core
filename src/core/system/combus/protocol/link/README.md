# Links

This folder answers three questions: how is a link described, how does it start, and how do we know it is lost?

## Why Links

A link carries no byte. It exists so that nothing is wired in the code: which port carries which channels, in which direction and at what rate, is left to the configuration. For each connection, a link joins the protocol and the hardware, with two roles:

- **a mapper**, on the hardware side: it puts a logical link (`ComDev`) on a physical port (`ComPortCfg`), with the role of this end (TX, RX or both). See [Describing a Link](#describing-a-link);
- **an orchestrator**, on the protocol side: at boot, it has its port set up, sets its contract and starts its TX and RX; while it runs, it watches its state and reports its loss to the failsafe. See [Starting](#starting) and [Watching](#watching).

## Describing a Link

A link is declared in a configuration file, not programmed, with the following components:

| Structure | Role | Where |
|---|---|---|
| `ComPortCfg` | the physical port of a board | `core/system/hw/com_port.h` |
| `ComProtocolCfg` | line rate, frame rate, loss timeout, startup grace; the same at both ends | `combus_link_defs.h` |
| `ComDev` | the logical link: its scope, its type (one way or both ways), its activation | `combus_link_defs.h` |
| `ComDevMap` | the wiring of one end: a `ComDev` on a `ComPortCfg`, as `TX`, `RX` or `TX_RX` | `combus_link_defs.h` |
| `ComPeerLink` | the table of a link between nodes, generated by the builder | `combus_peer_link_defs.h` |

The same `ComDev` is shared by both ends; each one wires it on its own port. A `ComDev` is **transport-agnostic**: it says what the link carries and how, never over what. The medium is the business of the `ComPortCfg`, so the same `ComDev` can run over a wire or a radio link.

A board lists its links in a table of `ComDevMap` next to its ports (`comLinks[]` of its `envCfg.h`); the remote lists the machines it drives (`remotes/config/driven_machines.h`).

### The Two Scopes

| Scope of the link | Connects | Channels carried |
|---|---|---|
| `INTER_NODE` | two nodes (remote, trailer...) | `BASE` |
| `INTRA_NODE` | the boards of one node | `SYSTEM`, which includes `BASE` |

`BOARD` channels stay on their board: they never travel.

A link between nodes may also have **its own table** (`ComPeerLink`): this is the case of a link through a coupler and of the link with the remote. It then carries exactly the channels of that table.

## The Running Link

The description is what the configuration declares; the **`ComBusLink`** is what the code runs. At boot, each `ComDevMap` of the board becomes one `ComBusLink` (`combus_link_defs.h`): everything one end needs to run its link.

| Part | Content |
|---|---|
| Identity | its name, the layer it writes with (given by its scope), its table if it has one |
| Transport and contract | the `ComPort` of the port, and the context of the contract, shared by both sides |
| Transmission | the size of its frames and their rate; absent if this end does not transmit |
| Reception | the size of its frames, its receive buffers and the ComBus it writes to; absent if this end does not receive |

## Starting

A link is established in two phases: the board sets it up at boot, then both ends agree on what they exchange. No data is applied before that agreement.

### At Boot

`combus_links_init()` starts from the table of `ComDevMap` of a board:

```text
For each ComDevMap:
    combus_link_check()             refuses a wrong description, before taking the port
    set up the port                 gives a ComPort
    combus_link_build()             fills the ComBusLink

Register the TX and RX states
combus_link_start()                 contract of the link, then TX and RX sides, for each link
combus_link_supervisor_start()      puts the links under watch
```

1. **Check.** `combus_link_check()` refuses a description that cannot work, before the port is taken:
   - a missing device, port or protocol;
   - a coupled link without its coupling device or its table;
   - a two-way link not wired `TX_RX`, or a one-way link wired `TX_RX`;
   - a frame rate of 0 or above 1000 Hz, or a receiving end without a loss timeout;
   - a line rate above what the port accepts;
   - a line too loaded: above 70 % of its rate, the link starts with a warning; above 100 %, it is refused;
   - a table on a link between boards, or a table too large for the receive buffers.
2. **Open.** The `ComPortCfg` is opened and gives a `ComPort`, the only interface the protocol talks to.
3. **Build.** `combus_link_build()` fills the `ComBusLink` of the link, and prepares what the watch will need.
4. **Start.** `combus_link_start()` prepares the contract: the MD5 expected from the other end, and whether this end must wait for an ACK. The contract starts `UNKNOWN`. Then the TX and RX sides start.
5. **Watch.** `combus_link_supervisor_start()` puts every link under watch. A link through a coupler starts off, until it is paired.

A failed link stays inactive and is reported in the log; the others start anyway. All the storage belongs to the caller and stays static.

`combus_link_check()` and `combus_link_build()` do not touch the hardware: they can be tested on the board without any wiring.

### Agreement

From the first loop cycle, each end sends handshake requests that carry the MD5 of its channels. As long as the MD5 differ, the contract stays `UNKNOWN`: the data frames received are ignored, and a two-way end sends none. When they match, the contract becomes `STABLE`, and the data flows.

The link counts as `ALIVE` at its first data frame applied. See the [handshake](../handshake/README.md) for the sequence, and [coupling](../coupling/README.md) for a link that waits to be hitched.

## Watching

`combus_link_supervisor_update()` runs on every loop cycle. A receiving link has three states:

| State | Meaning |
|---|---|
| `NEVER_SEEN` | no frame since the watch started |
| `ALIVE` | a recent frame, under a valid contract |
| `LOST` | seen, then silent for longer than `linkTimeoutMs` |

### When a Link Counts as Lost

It depends on its scope, and the result feeds a failsafe contributor. The chain that reads it decides the severity.

| Link | Counts as lost | Contributor |
|---|---|---|
| between boards | `LOST`, or never seen once the startup grace is over: the boards start together | `BOARD_LINK_FAIL` |
| to another node | not `ALIVE`, without any grace: the other node may not be there | `NODE_LINK_FAIL` |
| through a coupler | see [coupling](../coupling/README.md) | the one of its `CouplingDev` |

A send-only link never counts: it cannot know anything about the other end.

### Safe Values

When a link with a table stops being alive, what this node received through that link returns to its safe value, the `value` declared in its `.cb`. What the node sends does not move, and a `both_or` channel is not concerned, since a frame never writes it. A link without a table changes nothing.
